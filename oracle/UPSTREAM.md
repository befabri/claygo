# Tracking upstream Clay

The `oracle/` harness compiles a **pinned snapshot** of upstream
[clay.h](https://github.com/nicbarker/clay) and dumps a corpus of layout scenes
to `../testdata/*.golden.json`; the Go tests prove the port reproduces that
output byte-for-byte.

- `clay.h` — verbatim upstream header. Never edit by hand.
- `CLAY_VERSION` — provenance: the exact upstream commit `clay.h` came from
  (the header's own `VERSION: 0.14` spans ~100 commits, so this is what pins it),
  plus the list of extension patches applied on top (see Extensions).
- `patches/<name>.h` — a claygo extension's functions, as ordinary C. Edit
  directly.
- `patches/NNNN-<name>.patch` — that extension's splice into `clay.h`: fields,
  one-line hooks, and the `#include` of the header. Edited only through
  `make rebase-patch` / `make refresh-patch` (see Extensions).
- `clay_ext.h` — generated by `make`: `clay.h` with every patch applied. Not
  committed.
- `main.c` — hand-written scene corpus + JSON dumper, mirrored on the Go side by
  `goldenScenes` in `scenes_test.go`. Two independent implementations is what
  makes the parity test meaningful, so neither is generated.

`make` builds two binaries: `oracle` from `clay_ext.h` (every scene) and
`oracle-upstream` from the verbatim `clay.h` with `-DCLAY_ORACLE_UPSTREAM`
(upstream scenes only). `make regenerate` takes upstream goldens from
`oracle-upstream` and extension goldens (`ext_` prefix) from `oracle`;
`make verify` additionally checks that `oracle` reproduces every upstream
golden, which is what proves the patches leave upstream behavior alone.

## Bumping Clay

```sh
make -C oracle update-clay REF=v0.15              # tag, branch, or full SHA
make -C oracle update-clay CLAY_SRC=../.reference/clay   # offline, from a local clone
```

This re-vendors `clay.h`, rewrites `CLAY_VERSION`, re-applies the extension
patches, and regenerates the goldens. If a patch no longer applies the script
stops before regenerating and says so; rebase the patch first (below).
Then `git diff testdata/` shows exactly which scenes upstream changed, and
`go test ./...` says whether the port still matches. If the diff is non-empty,
commit `clay.h` + `CLAY_VERSION` + `testdata/` together; if `go test` fails, the
failing scenes pin what to fix in the Go port first.

## Adding a scene

Touch three places, then `make -C oracle regenerate && go test ./...`:

1. `main.c` — the C scene function + a `SCENES[]` entry.
2. `scenes_test.go` — the Go builder + a `goldenScenes` entry.
3. `testdata/<name>.golden.json` — regenerated, never hand-written.

`parity_test.go` fails if these lists fall out of sync.

Extension scenes follow the same three steps with the `ext_` prefix, inside
`#ifndef CLAY_ORACLE_UPSTREAM` in `main.c` and in `extensionScenes` in
`scenes_ext_test.go`.

## Extensions

claygo carries features upstream Clay does not have. Each one is a documented
divergence: a zero-value-off field, a C reference implementation as a patch on
the verbatim header, `ext_` goldens produced by that patched oracle, and Go
code physically separated from the ported files. The default path stays
byte-identical to upstream; `make verify` proves it every run. The process
for adding one, and the checklist of what has gone wrong before, is
`docs/extensions.md`; this section is the catalogue.
